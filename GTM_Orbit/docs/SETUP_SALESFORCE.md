# Salesforce setup (optional)

This guide loads the 10 demo accounts into your own Salesforce org and syncs them into Snowflake. Opt-outs and
missing contacts then come from a real system of record, and you can show them in Salesforce during a demo.

You don't need this to run GTM Orbit. Without it, run `snowflake/05_salesforce_sample.sql`, which loads the same
records with stand-in IDs.

[← Back to README](../README.md)

## What gets created

| Object | Count | Notes |
| --- | --- | --- |
| Accounts | 10 | `AccountNumber` values `GTM-0001` to `GTM-0010`; the demo only ever touches these |
| Contacts | 29 | Includes opted-out contacts (Morgan Ellis at Northstar; everyone at Verdant) and one with no title or email (Cobalt) |
| Opportunities | 13 | Open, closed-won and closed-lost |
| Cases | 7 | Including an escalated integration case at Harborline |

The account owner is the user you log in as.

## Step 1: Get a Salesforce org

Use a free [Developer Edition](https://developer.salesforce.com/signup) org, or any sandbox where you can create
records. Don't use a production org.

## Step 2: Install the Salesforce CLI and log in

```bash
npm install -g @salesforce/cli
sf org login web --alias gtm-demo
```

A browser window opens. Sign in to the org and allow access.

## Step 3: Create the records

From `GTM_Orbit/`:

```bash
sf apex run --file scripts/seed_salesforce.apex --target-org gtm-demo
```

The script is safe to re-run. It first deletes any existing `GTM-*` demo records and their contacts,
opportunities and cases, then creates them fresh. It runs as anonymous Apex, so it also sets fields like
**Email Opt Out** that some profiles can't edit through the import wizard.

To see the records: `sf org open --target-org gtm-demo`, then open **Accounts**, switch the list view to
**All Accounts**, and open **Northstar Field Services → Contacts**.

## Step 4: Export the records and build the sync file

```bash
bash scripts/export_salesforce.sh          # writes salesforce/export/*.csv
python3 scripts/build_sfdc_sql.py          # writes snowflake/05_salesforce_sync.sql
```

The script uses the `gtm-demo` alias by default. Set `SF_TARGET_ORG=<alias>` to use another one.

## Step 5: Load the records into Snowflake

Run `snowflake/05_salesforce_sync.sql` in Snowflake (see [How to run a SQL file](SETUP_SNOWFLAKE.md#how-to-run-a-sql-file)).
It replaces the four `RAW_SFDC` tables and `APP.AE_DIRECTORY`.

Both `salesforce/export/` and `05_salesforce_sync.sql` are git-ignored, because they contain your org's record IDs
and your user's name and email.

Whenever you change records in Salesforce, repeat steps 4 and 5. The sync is a simple batch reload; in production
this would be a connector or a scheduled pipeline.

## Changing the demo data

The import files in `salesforce/*.json` and the Apex script are generated by `data/generate_data.py`, together with
every Snowflake seed. To change accounts, contacts or calls:

```bash
python3 data/generate_data.py          # regenerates salesforce/*.json, snowflake/seed/*.csv
python3 scripts/build_apex_seed.py     # rebuilds scripts/seed_salesforce.apex
python3 scripts/build_seed_sql.py      # rebuilds snowflake/04_seed_data.sql
python3 scripts/build_sfdc_sql.py --sample   # rebuilds snowflake/05_salesforce_sample.sql
```

Then re-run the affected steps. If you change the demo stories, also update `APP.SCRIPTED_DRAFTS` in
`07_scripted_agents.sql`. Then rebuild the offline snapshot with `python3 scripts/build_orbit_fixtures.py`. That
script reads `salesforce/export/`, so run step 4 first, and the snapshot will carry your org's IDs and owner
name.

## Remove the demo records

Run this anonymous Apex, for example in **Developer Console → Debug → Open Execute Anonymous Window**:

```apex
List<Account> old = [SELECT Id FROM Account WHERE AccountNumber LIKE 'GTM-%'];
delete [SELECT Id FROM Case WHERE AccountId IN :old];
delete [SELECT Id FROM Opportunity WHERE AccountId IN :old];
delete [SELECT Id FROM Contact WHERE AccountId IN :old];
delete old;
```
